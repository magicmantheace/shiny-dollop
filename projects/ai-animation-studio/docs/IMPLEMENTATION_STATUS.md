- F3 slice 2 — offline TTS cache + phoneme timing (2026-11-03): `studio/voice.py` defines the voice engine interface (`synthesize(line, voice, timing, duration_ms=None) -> ClipResult` carrying WAV bytes, duration and engine name; engines never write files and never touch the network) with two engines — `StubVoiceEngine` (deterministic, offline: a valid silent WAV at 16000 Hz 16-bit mono whose duration is EXACTLY the ADR-009 speak hold for the line under the given `TimingConfig`, explicit `duration_ms` honored the same way; 16 frames per millisecond makes every hold sample-exact) and `ExternalVoiceEngine` (the slot for a future espeak/piper-style CLI engine: an injectable `runner(argv, input_text) -> bytes`, `{voice}` substituted into the argv template, the line passed as the input text, `VoiceError` on runner failure or non-WAV output, and the clip duration read from the produced audio rather than assumed). `phoneme_table(line, hold_ms)` emits an ESTIMATED word-level alignment — one segment per word partitioning the hold proportionally to word length (largest-remainder distribution: contiguous, first starts at 0, last ends at exactly the hold) with a coarse viseme label per word from a small documented onset rule (digraphs first, then first letter; letterless words are `sil`) — the data path a blendshape-capable rig would consume; there is no acoustic analysis. `VoiceCache` stores clips as `<key>.wav` in a directory outside git (constructor argument, else `AI_ANIMATION_VOICE_CACHE`, else `<system temp>/ai-animation-studio/voice-cache`) keyed by SHA-256 of the canonical JSON of engine name, voice, line, timing rate + clamps and explicit duration; a repeat call returns the stored clip without re-synthesizing, and no index file is kept — the record (key, engine, voice, line hash, duration, WAV length + SHA-256, phoneme table) is reconstructed from the stored WAV, and a corrupt entry re-synthesizes. The new `studio speak` CLI command (`--line`, `--voice`, `--engine stub|external`, `--voice-cmd`, `--voice-cache`, `--rate`) prints the clip record and never touches the scene runtime files. - F5 slice 1 — background job queue + worker runner + validation previews (2026-11-03): migration 3 adds a `jobs` table to the library database (kind, JSON payload, state queued/running/done/failed, worker id, attempts, JSON result or error text, created/claimed/finished timestamps; fresh and v1-shaped databases reach it through the migration framework with rows intact). `studio/jobs.py` is the queue API: `enqueue` (payload validated as JSON-serializable on write), `claim` (oldest queued job first, taken inside a `BEGIN IMMEDIATE` transaction so two workers can never claim the same job; `attempts` counts claims), `complete`/`fail` (running jobs only; result/error and finish timestamp recorded), `requeue_stale` (a running job whose claim is older than the given age returns to `queued` with worker/claim cleared — unless it has already been claimed `MAX_ATTEMPTS` = 3 times, in which case it is marked `failed` with a named error instead), `get_job`/`list_jobs`. - Lantern generator platform determinism (2026-11-07, ADR-010): the F5.3 generator's byte-identity held per platform but not across them — on the owner's Windows PC it produced a different SHA-256 than on this Linux VM, so the ADR-008 `hash_match` promotion gate refused the PC-generated file. Root cause (proven, see the Verified section): CPython `math.sin`/`math.cos` delegate to the platform C library and glibc vs the Windows CRT round the last bit differently; the hexagon flat normals subtract nearly equal sines, so 12 float32 normal lanes carried a ~1e-16 cancellation residual that is pure libm rounding noise. Fix: `tools/generate_lantern.py` now computes sine/cosine in pure Python (quadrant reduction against a two-part pi/2, Taylor/Horner polynomials; only +, -, *, / reach the output — all IEEE correctly rounded; `math.sqrt` kept, correctly rounded by IEEE mandate). The generated lantern is unchanged as geometry: every position float32 is identical to before, the only changed values are the noise residuals themselves plus one accessor bound's last-ULP decimal repr. The pinned hash changed once — `examples/lantern_procedural_catalog.json` now pins `897850a9…` (33,148 bytes), also pinned as a literal in `tests/test_create_promote.py`, which gains a libm-perturbation regression test (perturbing every `math.sin`/`math.cos` result by 1 ULP must not change a byte). **Verified byte-identical across platforms**: the fixed generator run on the owner's Windows PC (Python 3.14.2) via the Muse PC Bridge produced exactly the VM's bytes (SHA-256 `897850a9…`, `cmp` clean) — see the Verified section. Any pre-existing local asset-store copy of `lantern_procedural_01.glb` still hashes to the old value and must be regenerated with the committed generator before promotion; the committed catalog intentionally stays `candidate` (promotion remains a local explicit act). Full suite 334 tests OK.

### Lantern generator platform determinism (2026-11-07, Linux VM + owner Windows PC via the Muse PC Bridge)

- **Reproduction (pre-fix generator, committed version):** VM (Python 3.12.3, glibc) -> 33,144 bytes, SHA-256 `474e095c71c3df1dd3fd80662f860c06087a0e63d758b305c0bd240ced3244ff` (the old catalog pin). The identical script run on the owner's PC (AthenZ971, Windows 11, Python 3.14.2) via the PC Bridge -> 33,144 bytes, SHA-256 `ea23535b6204f89c6cf6f8f1377b2727aadcf3ea99838302693f5150b660c09b`. Byte diff of the two GLBs: JSON chunks identical; exactly 12 of 7,920 float32 lanes differ, all in the frame NORMAL accessor, all the same near-zero x-component of the hexagon side-4 flat normals (base prism + top cap): VM `-2.238352855150861e-16` vs PC `-1.1191764275754305e-16` (exactly 2x).
- **Root-cause proof:** that normal's x-component is `dy * (R sin(2pi*5/6) - R sin(2pi*4/6))` normalised — a difference of two sines whose true values are equal (60-digit Decimal computation of the exact double arguments gives a residual of -1.14e-17, vs glibc's -1.38e-17: the value is rounding noise, not signal). Recomputing the component on the VM with only `sin(2pi*5/6)` perturbed by +1 float64 ULP (`math.nextafter`) reproduces the PC's packed float32 **exactly** (`-1.1191764275754305e-16`): one last-bit libm difference, amplified by cancellation, is the whole divergence.
- **Fix:** pure-Python `_sin`/`_cos` in `tools/generate_lantern.py` (two-part pi/2 quadrant reduction + Horner Taylor polynomials; max deviation from the platform libm over [0, 2*pi] measured at 1.11e-16, ~1 ULP). Vs the pre-fix VM output, the fixed build changes no position float32, one accessor bound's float64 repr in its last ULP, and the 12 noise-residual normal lanes; total 33,148 bytes.
- **Cross-platform proof (post-fix):** VM build -> SHA-256 `897850a928874d12d77dcfc193f3f147a3d6dff89bf924c122dbcb6119fe90a8`; the same committed script run on the owner's PC via the PC Bridge -> the identical SHA-256, and the downloaded PC file is byte-identical to the VM file (`cmp` clean). PC-side repro files were deleted afterwards; no process was left running on the PC and nothing required a UAC prompt.
- **Tests:** full suite `python3 -m unittest discover -s tests` -> `Ran 334 tests`, `OK` (332 prior + 2 new in `tests/test_create_promote.py`: the output hash pinned as a literal constant, and the libm-perturbation regression — every `math.sin`/`math.cos` result perturbed by 1 ULP leaves the output byte-identical). The chain test still passes the real ADR-008 gates against the new pin. No lint/typecheck tooling is defined in this project (stdlib-only, `pyproject.toml` declares no dev tools), so the suite is the check.
- **Boundary:** byte-identity is proven for the two platforms/Python versions above (3.12/glibc, 3.14/Windows CRT); the mechanism (correctly rounded ops only) is platform-general, but no third platform was run. Visual equivalence is by the numbers (positions bit-identical, normals differ only in ~1e-16 components of unit normals); no on-screen render of the regenerated lantern was made, and the promotion's human gates (`visual_review`, `owner_hardware_visual`) remain pending as always.
