# Crawl v0.4 — Slices 7–11 Gameplay Batch

## Status

Implementation branch: `agent/crawl-v0.4-slices7-11`

Base branch: `agent/crawl-v0.4-slices2-6`

This batch deliberately stacks on the Slices 2–6 autonomous-agent foundation. Fixes found during the Slices 1–6 evening validation should be applied to the lower branch first, then carried forward into this branch before the Slices 7–11 validation pass.

## Slice 7 — Individual Combat, Injury, and Death

Implemented in:

- `src/livingworld/combat_system.py`
- `src/livingworld/gameplay_domain.py`

The combat model is deterministic from crawl seed, encounter ID, round, actor, target, and roll channel.

Crawler combat state uses:

- melee/ranged/ability skill,
- defense,
- equipment attack/armor/accuracy/evasion,
- progression modifiers,
- stamina,
- injuries,
- current health.

Enemy combat state uses reusable archetypes:

- brute,
- skirmisher,
- stalker,
- caster,
- guardian.

Combat supports:

- hit and miss resolution,
- damage variance,
- armor/defense mitigation,
- evasion,
- stamina costs,
- deterministic target selection,
- bounded retreat decisions,
- group encounters,
- enemy defeat,
- crawler death,
- death item drops,
- structured combat events.

Injuries currently include:

- bleeding,
- impaired movement,
- reduced accuracy,
- reduced stamina,
- schema support for incapacitation.

Bleeding can continue damaging a crawler during combat and can cause death.

Death routes through the existing Crawl lifecycle elimination path so survivor counts remain authoritative.

### Slice 7 acceptance mapping

- identical seed/state -> reproducible combat decisions and rolls,
- group encounters are supported,
- retreat is supported,
- death persists in crawler participation state,
- inventory is dropped rather than duplicated/deleted,
- combat start/hit/injury/death/end events are emitted.

## Slice 8 — Items, Equipment, Loot, and Consumables

Implemented in:

- `src/livingworld/gameplay_domain.py`
- `src/livingworld/item_system.py`
- Crawl-level validation in `src/livingworld/crawl_domain.py`

Items track:

- stable item ID,
- name,
- category,
- rarity,
- equipment slot,
- stats,
- effects,
- durability,
- requirements,
- owner/location/encounter holder,
- provenance event references,
- importance marker.

Categories include:

- weapon,
- armor,
- consumable,
- trinket,
- resource schema support.

Rarities include:

- common,
- uncommon,
- rare,
- epic.

The core invariant is:

> Every live item has exactly one authoritative holder: a crawler, a floor location, or an encounter.

Crawl validation also checks that:

- an owned item appears in exactly one owner inventory,
- an inventory item points back to its owner,
- equipped items remain in inventory,
- ground item locations exist,
- encounter-held rewards reference a real encounter.

Loot can be:

- generated by encounters,
- awarded to a crawler,
- equipped automatically according to crawler/build value,
- consumed for healing/stamina,
- dropped on death,
- recovered from the ground.

Rare/epic items are marked important for later history/highlight logic.

## Slice 9 — Progression, Abilities, and Builds

Implemented in:

- `src/livingworld/progression_system.py`
- `CrawlerProgression` in `gameplay_domain.py`

Progression state tracks:

- level,
- current XP,
- advancement points,
- specialization,
- unlocked abilities,
- passive modifiers,
- choice history.

Initial specializations are original Crawl backend placeholders:

- `vanguard`,
- `hunter`,
- `survivor`,
- `mystic`.

These names and their presentation can change later without changing the progression contract.

Specialization selection is based on crawler skills and personality rather than a universal best build.

Examples:

- defense/melee/loyalty/courage push toward Vanguard,
- ranged/perception/stealth/caution push toward Hunter,
- medicine/scavenging/empathy/patience push toward Survivor,
- ability skill/curiosity/risk tolerance push toward Mystic.

Each tree currently contains three ability hooks followed by repeatable mastery investment.

Combat consumes the resulting attack/defense/accuracy/evasion modifiers.

### Slice 9 acceptance mapping

Two crawlers can start with the same ruleset and diverge into different specializations/abilities because their profiles and experiences differ.

## Slice 10 — Parties, Alliances, and Group Behavior

Implemented in:

- `src/livingworld/party_system.py`
- group routing in `src/livingworld/gameplay_simulation.py`
- party-aware reward distribution in `src/livingworld/encounter_system.py`

Parties are not assigned at crawl creation.

Co-located ungrouped crawlers evaluate compatibility from:

- sociability,
- loyalty,
- reciprocal trust,
- resentment.

Compatible crawlers may form bounded parties of up to five in this initial implementation.

Leadership is selected from leadership skill and sociability.

Loot policy emerges from group personality and can be:

- need before greed,
- finder's keepers,
- equal share,
- leader assignment schema support.

Party behavior currently influences:

- route following,
- shared combat participation when co-located,
- loot allocation,
- social familiarity,
- post-encounter relationship changes,
- leader succession,
- dissolution.

Parties update after deaths/eliminations. Non-active members are removed from active membership, and a dead leader can be replaced.

Cohesion is recalculated from current member compatibility. Very low cohesion dissolves the party.

A rescue-willingness rule is exposed for later active rescue behavior.

## Slice 11 — Encounters, Enemies, Traps, and Hazards

Implemented in:

- `src/livingworld/encounter_system.py`
- `EncounterState` / `EnemyState` in `gameplay_domain.py`

Each generated floor can seed deterministic location encounters.

Initial encounter categories include:

- ordinary hostile,
- elite,
- boss,
- trap,
- environmental hazard,
- resource dilemma.

Schema types are also reserved for:

- social dilemma,
- timed threat,
- pursuit,
- rescue.

Each encounter tracks:

- ID,
- floor/location,
- type,
- status,
- difficulty,
- trigger,
- participating crawlers,
- enemies,
- rewards,
- possible outcomes,
- failure consequences,
- cleanup status,
- resolution tick.

Hostile/elite/boss encounters invoke deterministic combat.

Trap/hazard encounters use crawler perception, trap skill, caution, and seeded resolution.

Resource dilemmas resolve without combat and can still award loot/progression.

Resolved encounters explicitly set `cleanup_complete`.

## Integrated Gameplay Loop

`GameplayCrawlSimulator` combines Slices 2–11.

One simulation tick now performs roughly:

```text
crawler-local perception
-> utility decision
-> optional healing consumable
-> independent destination choice
-> party route influence
-> movement
-> knowledge/memory update
-> emergent party formation
-> ground-loot recovery
-> location encounter trigger
-> combat/hazard/opportunity resolution
-> death/injury/reward processing
-> XP/build advancement
-> relationship consequence
-> party stability update
-> floor completion check
```

If all current-floor crawlers die, the floor is marked failed and the crawl enters a terminal completed state with `CRAWL_ENDED_NO_SURVIVORS` recorded. A richer failed/ended crawl lifecycle can be separated in Slice 12 when deadlines and intermission are implemented.

## Deliberately Deferred

This batch does not implement:

- floor deadline closure/elimination,
- formal intermission state,
- the Crawl Director,
- full rescue actions,
- active trading/negotiation transactions,
- crafting,
- advanced ability targeting/effects,
- spatial tactical combat beyond graph-location abstraction,
- persistent enemy pursuit across rooms,
- full boss mechanics/phases,
- story/highlight scoring metadata,
- replay checkpoints,
- Unreal rendering,
- commentary/media production.

Those belong to later roadmap slices.

## Batch Acceptance Gate

Before merging this stack, local testing should prove:

1. Slice 1–6 regressions remain green,
2. combat is deterministic for identical state,
3. no item duplication/invalid ownership occurs through loot, consumption or death,
4. crawler death updates authoritative counts and state,
5. parties form/dissolve without broken membership references,
6. encounter cleanup never leaves invalid crawler/item/location references,
7. progression survives the integrated run and produces divergent builds,
8. a multi-floor autonomous gameplay run reaches a terminal state within the configured step budget,
9. the complete Crawl model validates after the run,
10. the inherited repository regression suite remains green,
11. no GitHub Actions minutes are required.
